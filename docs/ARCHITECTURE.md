# Architecture and persistence

Two crates are justified now: `kuro-core` holds typed study models, validation, accuracy, revision and backup algorithms; `kuro-web` renders Dioxus 0.7.10 components. No empty native applications are advertised. Cargo.lock pins dependencies. The current stable version was checked against crates.io; dx reports 0.7.10.

The browser adapter in `apps/web/public/storage.js` owns IndexedDB transactions, file dialogs/downloads, local-date formatting and recovery-draft storage. Study logic is Rust. State schema 1 has a monotonically increasing revision. Every update validates in Rust, compares the current IndexedDB revision, and commits in one read-write transaction. UI success follows transaction completion. A stale tab must reload; it cannot replace newer records. Unknown or malformed state is protected from overwrite. Schema 1 is the first schema; no upgrade from a previous application schema is implemented or claimed. IndexedDB version 1 creates the state store via its upgrade transaction.

This first storage design keeps the study snapshot in one record. This simplifies atomicity but requires O(n) serialization per save and is unsuitable for large document blobs or very large histories. A later schema must split entities and assets and migrate transactionally. No large-data performance claims are made.

Notes maintain a per-tab localStorage recovery draft synchronously on input. A titled draft autosaves to IndexedDB after 600ms. Failed writes are visible and do not update committed state. Recovery drafts are additional browser data, not an unlimited guarantee. Closing a tab before autosave leaves a recovery key, but this build does not provide an orphan-draft browser; keep the tab/session or export saved data. Note editor navigation during the 600ms delay can preserve a draft without immediately committing it. Backups include committed notes only. A successful restore clears the current tab's recovery draft. Drafts in other open tabs are independent; close other tabs before restoring.

Backups are a portable JSON envelope with a version, exact serialized payload and SHA-256 digest. The digest detects damage; it is not encryption or an authenticity signature. Import checks the envelope, digest, schema, IDs, dates, theme and field limits before asking the user to replace data. A failed transaction preserves original state. The user is instructed to export current data first. Exported data can be restored in a clean browser context (covered by E2E).

`Repository` and `MusicProvider` define initial shared contracts. Browser APIs are confined to the web crate; no SQLite implementation, secure credential adapter, native file picker, native MusicKit bridge, background timer, or native app has been implemented. Native support requires actual platform adapters plus per-platform packaging and runtime tests. A web build is not proof of native support.

Security boundaries: no secrets, private keys or tokens are included. Note text renders as text, never raw HTML. Imports have a 20MB pre-read size limit. Unknown JSON fields are rejected. Private files are not uploaded. Streaming controls are unavailable until legitimate provider implementations are tested. Dependencies use normal TLS/integrity verification; no verification bypass is configured.

The portable backup envelope is limited to 20 MB on both export and import. Above that supported limit export reports an error; no unusable backup is presented as successful. Large-data incremental exports are future work. Note switching saves a titled unsaved note before replacing its recovery draft. Transaction tasks are owned by the root application scope so ordinary module navigation does not cancel the final state update.
